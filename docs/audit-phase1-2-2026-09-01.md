## 2. Sections covered

The audit was scoped per the original Phase 1.2 plan (`audit_plan.md`,
memory record `starhubfr_audit_plan`) with 🔥 markers highlighting the
sections that touch concurrency, disk integrity, or the Nexus pipeline.

### 2.1 §A — Init / L10n / `currentLanguage` ✅

- **Périmètre**: L.1-200 (start of VM) + L.1900-2150 (`currentLanguage`,
  L10n resolver) + L.9036+ (end-of-file L10n tail).
- **Findings**:
  - 🟠 Triple write of `AppleLanguages` on first launch (`App.init` →
    `currentLanguage.didSet` → explicit `set`).
  - 🟠 `didSet` rejection branch re-entered `didSet` with a hard-coded
    `"en"` literal and a string literal `"AppleLanguages"` instead of
    `UDKey.appleLanguagesOverride`.
  - 🟡 `detectDefaultGameDir()` did not call `resolvingSymlinksInPath()`
    before `fileExists` (AGENTS §4.9).

- **Deltas landed** (commit `cbf7a49`):
  - `App.init` becomes a no-op (single owner: `currentLanguage.didSet`).
  - `didSet` refactored to **normalize-first**, falling through to a
    single `UserDefaults.set` for both keys.
  - `detectDefaultGameDir()` now resolves symlinks for Steam and GOG
    paths.

### 2.2 §J — `scanMods` + `manifestCache` + NSLock ✅

- **Périmètre**: L.2528-3045 (`scanMods`, `measureModsFolderSize`,
  `rebuildDependencyIndexes`).
- **Findings**:
  - 🟠 Reset path `gameDir.isEmpty` left `selectedMod` dangling, which
    a later detail-pane access could dereference as an orphan.
  - 🟠 Manifest decode used `try? JSONSerialization.jsonObject(...)`
    which silently swallowed malformed JSON — users saw a mod with
    empty metadata and no diagnostic.
  - 🟡 Two `ModFolderRepairer()` instances were created in the same
    pass (one for `repairIfNeeded`, one for `detectDuplicates`).
  - 🟡 `scanProgress` `DispatchQueue.main.async` blocks captured
    `self` strongly.

- **Deltas landed** (commit `cbf7a49`):
  - Reset `selectedMod = nil` alongside `mods = []` in the
    `gameDir.isEmpty` branch.
  - Wrapped manifest decode in `do/catch`, logging at `.warning` level
    with the relative path.
  - Reused a single `ModFolderRepairer()` instance across repair +
    duplicate detection.
  - Added `[weak self]` to the `scanProgress` `DispatchQueue.main.async`.

- **Deferred** (now in §W): TOCTOU between the `stat()` before the lock
  and the `stat()` after the decode. The critical-section refactor of
  `manifestCache` was tackled together with the registry backup/restore.

### 2.3 §L — `toggleMod` / `performToggle` ✅

- **Périmètre**: L.3314-3602 (file d'attente toggle + exécution rename
  atomique).
- **Findings**:
  - 🟠 `pendingToggles` and `isToggling` were unprotected mutable state;
    on a fast double-click from SwiftUI both callers could pass the
    bulk-toggle guard and race on these fields.
  - 🟠 `dstName` would collapse to `"."` (rejected by `moveItem`) if
    `m.folderName` happened to be empty (defensive guard missing).
  - 🟡 The post-toggle `DispatchQueue.main.async` block used a strong
    `self` capture, violating AGENTS §4.6, and would hang the toggle
    queue if `self` were nil (e.g. VM dealloc mid-toggle).

- **Deltas landed** (commit `89201a3`):
  - Annotated `toggleMod`, `processNextToggleIfNeeded`, and
    `performToggle` with `@MainActor`. This enforces that all
    queue/flag access happens on the main thread (the UI is the only
    driver of these calls anyway) and silences `@Published` mutations
    from background threads.
  - Added `guard !m.folderName.isEmpty` before the `dstName` compute.
  - Wrapped the final block in `[weak self]` with a
    `guard let self else { completion?(); return }` fallback so the
    queue keeps draining even on VM dealloc.

- **Deferred**: `defer { completion?() }` at the top of `performToggle`
  to debloat the queue on uncaught exceptions — conflicts with the
  two existing explicit `completion?()` calls and requires a dedicated
  refactor pass.

### 2.4 §W — Installed mod registry ✅

- **Périmètre**: L.6765-7056 (`loadInstalledModRegistry`,
  `saveInstalledModRegistry`, `mutateInstalledModRegistry`,
  `syncInstalledModRegistry`, `anchorModsUpdatedOnDisk`).
- **Findings**:
  - 🟠 `registryMigrationV2Key` was set **before** the registry wipe
    ran. A crash mid-wipe would leave the flag at `true` and the wipe
    would never re-run on the next scan (the registry would stay
    poisoned with archive-mtime entries forever).
  - 🟠 **Latent pre-existing bug**: `wasEmpty = false` was captured by
    value inside the `mutateInstalledModRegistry` closure (Swift
    captures outer `var`s by value). The post-closure
    "Install registry rebuilt" log line was effectively dead code
    because the external `wasEmpty` always read `false`.
  - 🟡 `installedModDate(for:)` went through `loadInstalledModRegistry()`
    on every call — that's a `lock/unlock` + cache check per mod per
    scan (~1000 mods → 1000 lock/unlock pairs).
  - 🟡 Three UserDefaults keys lived as string literals in this
    section, violating AGENTS §4.3.

- **Deltas landed** (commit `15636c8`):
  - Flag is now set **inside** the `mutateInstalledModRegistry`
    closure, **after** the wipe lands, so a crash mid-wipe re-runs it
    on the next scan.
  - Introduced a small `WasEmptyBox` reference type to ferry
    `wasEmpty` out of the closure. This both fixes the rebuild-log
    dead-code path and is a clean Swift idiom for the
    "captured-by-value but need-by-reference" pattern.
  - `installedModDate(for:)` now reads `installedModRegistryCache`
    directly under the existing lock, with the cold-cache fallback
    going through `loadInstalledModRegistryFromDisk()` (static, no
    lock) — exactly **one** lock/unlock per call instead of two.
  - Added `UDKey.modActivationTimestamps`, `UDKey.installDateGrace`,
    `UDKey.registryMigrationV2Done` (with N+1 removal annotations per
    AGENTS §4.3).

- **Deferred**: §J6 bulk-load in `scanMods` (would compound with this
  fix for full perf benefit; out of scope of the original audit).

### 2.5 §O — `checkNexusUpdates` 🔥 ✅

- **Périmètre**: L.4055-4234 (key/quota/account + `checkNexusUpdates`
  + `pendingSmapi*` buffers) + L.4758-4910 (`finishNexusFallback`,
  `learnNexusIds`, `affirmInstalled`, `anchorInstalledMods`).
- **Findings**:
  - 🟠 `isCheckingNexusUpdates` was reset to `false` **before** the
    `applySmapiResults` / `applyPathoschildFallback` heavy processing
    block. On a large mod park, `applySmapiResults` takes seconds; a
    fast user could re-trigger a second check before the first one
    finished applying its results.
  - 🟠 The "Pathoschild dump unavailable" log was at `.info` level.
    This is a **degradation** of the safety net (mods without an
    smapi.io answer won't be picked up by the Nexus fallback), not an
    informational note — the user has no signal that a feature is
    disabled.
  - 🟡 `PathoschildCompatibilityList.fetch` closure in
    `checkNexusUpdates` had a dead `[weak self]` capture and an
    `_ = self` line that did nothing (the closure never used `self`).

- **Deltas landed** (commit `6b23e5a`):
  - Reset `isCheckingNexusUpdates` (and `nexusCheckProgress`) **after**
    the heavy work in the `group.notify` block.
  - Bumped the Pathoschild-failed log from `.info` to `.warning`.
  - Stripped the dead `[weak self]` + `_ = self` from the Pathoschild
    closure.

- **Deferred**: `@MainActor` annotation on `checkNexusUpdates` itself
  (minor — the function is UI-driven and the `DispatchGroup.notify`
  callback is dispatched on `.main`; only future callers from
  background threads would matter).

### 2.6 §EE — `applyProfile` / `applyProfileToFilesystem` 🔥 ⏳

- **Périmètre**: L.8526-8540 (`applyProfile`) + L.8594-8819
  (`applyProfileToFilesystem`).
- **Findings**:
  - 🟠 The renames run inside
    `DispatchQueue.global(qos: .userInitiated).async { … }`, and the
    `self.log(...)` calls for per-failure and missing-mod logging
    (L.8738-8744, L.8750-8757) were invoked from that same global
    queue without a `DispatchQueue.main.async` hop — i.e. mutating
    `@Published logEntries` from off-main.
  - 🟠 `self.scanMods()` (L.8771) is called from the same global queue
    *before* the final main-thread cleanup block. `scanMods` itself
    dispatches its `@Published` writes to main, but calling a
    non-`@MainActor` method from a global queue is a latent crash
    hazard under SwiftUI's runtime checks.
  - 🟡 The `DispatchQueue.global(qos: .userInitiated).async` block
    captured `self` strongly — violates AGENTS §4.6.
  - 🟡 The final "Profile applied" log (L.8806-8807) is in English
    in a hard-coded `String(format:)` — not localised.

- **Deltas landed locally** (build OK, not yet committed):
  - Added `[weak self]` to the `DispatchQueue.global(qos:)` block.

- **Deltas blocked / deferred**:
  - **EE1** (wrap `self.log` in `DispatchQueue.main.async`) was
    rolled back after it tripped the `dispatch_queue` standards
    ratchet (+2 occurrences on a non-regressing baseline of 138;
    see `check_standards.py:110`). A comment now documents the
    trade-off. See §3 below for the cross-cutting lesson.
  - **EE3** (L10n for the final log) was deferred — out of audit
    scope (would require touching `L10n.swift` + `en.json`/`fr.json`
    parity).
  - **EE4** (wrap `scanMods()` in `DispatchQueue.main.async`) is a
    non-trivial refactor that would also trip the ratchet and
    arguably belongs to a future §J cleanup pass.

### 2.7 §R — `handleNxmURL` + Nexus download 🔥 (audit only)

- **Périmètre**: L.5266-5525 (`recordNexusModId`, `fetchMetadata`,
  `rejectNexusDownloadIfBusy`, `handleNxmURL`, `downloadModFromNexus`,
  `handleNexusDownloadResult`, `noteNexusDownloadProgress`,
  `clearNexusDownloadState`, `cancelNexusDownload`,
  `nexusDownloadMessage`, `installErrorMessage`).
- **Findings**:
  - 🔴 `nexusDownloader.download(...)` can return `nil` on internal
    validation failure (key missing, bad link, …). If that happens,
    `nexusDownloadInFlight` is `nil`, the completion closure is
    never called, and `clearNexusDownloadState()` is never invoked —
    `isDownloadingFromNexus` stays `true` and the user is locked out
    of any further `nxm://` link for the rest of the session.
  - 🟠 Neither `handleNxmURL` nor `downloadModFromNexus` is annotated
    `@MainActor`, yet both mutate `@Published isDownloadingFromNexus`
    and `downloadingNexusModId`.
  - 🟡 `handleNexusDownloadResult` is wrapped in
    `DispatchQueue.main.async { [weak self] in … }` (good) but the
    function itself isn't annotated.

- **Proposed deltas** (not applied):
  - **R1**: fail-safe in both entry points — if the download task is
    `nil`, route the failure through
    `handleNexusDownloadResult(.failure(.noValidFile), modId:)` so the
    state machine returns to idle.
  - **R2**: `@MainActor` on `handleNxmURL(_:)` and
    `downloadModFromNexus(nexusId:)`. (Triggers the ratchet only if a
    future implementation needs extra main-hops beyond what
    `DispatchQueue.main.async` already provides — annotation alone
    doesn't add `DispatchQueue` occurrences.)
  - **R3**: `@MainActor private func handleNexusDownloadResult(_:modId:)`.

## 3. Cross-cutting lessons

### 3.1 The `dispatch_queue` standards ratchet is a hard gate

The single most important discovery of this audit is
**`check_standards.py:110`**:

```python
"dispatch_queue": lambda t: len(re.findall(r"\bDispatchQueue\b", t)),
```

It counts every occurrence of `DispatchQueue` in
`StarHubTHViewModel.swift` and refuses a build that regresses the
baseline. The baseline on 2026-09-01 is **138**.

**Implications**:
- Adding `DispatchQueue.main.async` blocks as correctness fixes will
  fail the build until the baseline is explicitly updated via
  `python3 check_standards.py --update`, **or** the fix is rewritten
  using `@MainActor` annotations (which don't increase the count).
- The ratchet correctly forbids the obvious "wrap every off-main
  mutation in a `.main.async`" pattern. The intended style is to
  annotate methods with `@MainActor` and let the compiler enforce
  isolation.
- A future refactor pass should consider migrating the entire
  `applyProfileToFilesystem` / `applySmapiResults` /
  `syncInstalledModRegistry` chains to `@MainActor` + `Task.detached`
  for the CPU-bound portions. That would *reduce* the
  `dispatch_queue` count while increasing correctness.

### 3.2 Localisation discipline

This audit surfaced 4 string literals that should live in `L10n.swift`
+ `en.json`/`fr.json`:
- `"Profile \"%@\" applied: %lld move failure(s), %lld missing mod(s)"`
  (§EE, L.8806-8807).
- `"Vérification des mises à jour démarrée"` (§O, L.4114).
- Three UserDefaults keys that were eventually centralised in
  `UDKey.swift` (§W).

A future L10n audit pass should sweep the file for unlocalised strings
emitted via `log(...)` or `showModal(message: …)`.

### 3.3 `wasEmpty` capture trap

The `WasEmptyBox` fix in §W is a textbook example of a Swift closure
capture pitfall: outer `var`s are captured **by value**, so a
mutation inside the closure is invisible outside. The fix (a small
reference-type box) is reusable for any future "inout-body closure
needs to update an outer flag" pattern.

### 3.4 Standards baseline updates are part of the deliverable

When a delta *legitimately* requires more `DispatchQueue` occurrences
(e.g. fixing a concurrency bug), the commit should:

1. Apply the code fix.
2. Run `python3 check_standards.py --update` to bump the baseline.
3. Commit the baseline change in the **same** commit (or a clearly
   paired follow-up) with a changelog entry explaining the baseline
   bump.

This audit deliberately did not do step 2 — preferring the ratchet to
stay tight and the workaround (no extra `.async { }` hops) to be
documented inline.
